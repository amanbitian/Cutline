# Remediation of the 2026-10-06 code review

Status of every finding in [CODE_REVIEW_2026-10-06.md](CODE_REVIEW_2026-10-06.md). The review reproduced eleven correctness failures and listed a further set of risks found by inspection. This file is the working list: what is fixed and how it is guarded, and what is still open, in the order it should be taken.

I independently re-ran the review's retained probe and all eleven failures reproduced with the same figures before any change was made. Performance consequences of the fixes are in [PERFORMANCE_LOG.md](PERFORMANCE_LOG.md).

**Rule for this list:** a finding is only marked fixed when a regression test that fails on the old behaviour is in the suite. Where I could, I confirmed the test fails against the old code rather than assuming it would.

## Milestone 1A: what was done, the policies it fixed, and what it found

Evidence and commands are in [MILESTONES.md](MILESTONES.md); the cost of the checks it added is in [PERFORMANCE_LOG.md](PERFORMANCE_LOG.md).

### Policies now enforced (and now documented where the code is)

- **Split preserves the rendered result.** For a reversed clip the left half keeps the *tail* of the source range. Keyframes are in clip-local time, so the right half's curves are rebased and the segment containing the cut is divided exactly.
- **A transition must join adjacent clips on its track, cover the cut, and match its alignment.** One rule, in SQL (`FindTransitionProblem`), used after every edit that can disturb a transition and by `ValidateDatabase()`. This is stricter than before: creation used to require only that the clips were on the same track. One existing test fixture declared a centre-aligned fade-in starting at its clip's first frame, which cannot be true; it is now `Start`-aligned.
- **An edit that disturbs the cut a transition joins removes that transition, in the same command.** The alternatives were refusing the edit (an ordinary drag would fail over something the editor did not touch) or leaving it dangling (the bug). The removal is undone by the same undo. Edits that leave the cut alone (trimming the far edge, a slip, reversing in place) keep it. Splitting moves the outgoing side to the right half, which is the half that now ends at the cut.
- **Track locks.** A locked track refuses every edit to its clips, its transitions, the effects and keyframes attached to either, its own effects, and removing the track. Deliberately outside the lock: the track's own state (so it can be unlocked), markers, and sequence-owned effects.

## Milestone 1B: what was done, and what it found

Evidence and commands are in [MILESTONES.md](MILESTONES.md); the measurements are in [PERFORMANCE_LOG.md](PERFORMANCE_LOG.md).

### Design decisions

- **One reader per stream, not a lock around a shared one.** A shared demuxer hands each packet to whichever decoder asked for the next one, so the other stream's packet is gone; a lock would only have made the loss orderly. Each `Source` now opens a demuxer per consumed stream (the probe's own context goes to the first), and tells the demuxer to drop every other stream. The cost is one more file handle and one more parse of the headers.
- **Source time zero is the earliest timestamp in the container.** One shared origin for every stream, so "the audio at source time t" and "the frame at source time t" are the same instant. A stream that starts late is silence until it starts. Previously each stream's raw timestamps were used.
- **A seek lands well before the target and the lead-in is thrown away**, because MDCT codecs and resampler filters need history to be right at the first sample kept. Near the start of the file the lead-in reaches before zero on purpose: an AAC priming frame sits there, and seeking to zero itself skipped it.
- **Resampling is aligned to whole samples.** The lead-in begins on a source sample whose position at the output rate is also whole (a multiple of source_rate / gcd), so output sample k is source sample k Ã— source rate / output rate exactly, and the resampler is flushed at the end of the stream.
- **Where a time base is coarser than a sample, count the packets.** Matroska counts milliseconds (48 samples at 48 kHz), so a packet's timestamp cannot place it; an exact index of start samples is built once, from packet sizes, on the first seek.

## Milestone 1C and the hardening that followed: what was done, and what it found

Evidence and measurements: [MILESTONES.md](MILESTONES.md) and [PERFORMANCE_LOG.md](PERFORMANCE_LOG.md).

### Design decisions

- **The mixer reads the snapshot, not a plan.** A plan is one instant; a block of audio is a span with edges, transitions and keyframes inside it. The mixer decides every sample itself, which is what makes blocks tile exactly (`BlocksOfAnySizeTileToTheSameAudioAsOneLargeBlock`, `RenderingInBlocksGivesTheSameSamplesAsRenderingAtOnce` on a real file) and removes the per-block scan of every clip in the project.
- **Pitch policy:** varispeed remains the exact fallback, and optional WSOLA pitch preservation was added later for supported forward rates, including varying speed curves.
- **Clip edges are placed on the nearest sample**, so a clip at the sequence rate is an exact copy of its source; a clip start between samples would otherwise be interpolated and softened.
- **Transitions play handles.** An outgoing clip continues into the media past its out point and an incoming one starts before its in point; where the media ends, that is silence rather than a held sample. A fade on one clip has no handle.
- **Head-trim animation stays on its frame.** The decision the 1A report asked for. A slip and a tail trim leave keyframes where they are.
- **Linked edits are transactional**, with a per-command opt-out and an explicit rule for what a cut does to the groups.
- **Post-commit work cannot fail a commit.** The database is the record; the package's journal copy and snapshots are reported as warnings.

# Cutline implementation status

This file distinguishes working software from architecture and roadmap. "Planned" means it is documented only; it must not be presented as implemented.

Detailed scope is tracked in 23 domain manifests under `parity/` and summarized by `premiere-parity-report.md`. Those manifests used to be hand-maintained and drifted from the code, so `scripts/cross-check-parity.js` now ties them to the test suite: a capability may not claim `implemented` without naming tests that exist, and the report generator refuses to build without that evidence. They still describe *scope* (220 items, most not started); the table below is the authority on what runs. `scripts/check-docs.js` checks that the test counts and file paths quoted in the markdown files are true of the code; run both in CI.

**Verified by 751 native tests** across 12 suites, including golden-frame image comparison, real FFmpeg decode, local proxy generation, offline speech/transcript behavior, UI-domain behavior and originals-only export. Build `scripts\build.bat`; test `scripts\test.bat`; walkthrough `build\native\cutline_demo.exe`; benchmark `scripts\bench.bat`.

## Known defects in capabilities marked Implemented

"Implemented" in the tables above means a working path with passing tests, not that every case is correct. An independent review on 2026-10-06 found defects in several of these, 11 of which it reproduced; [REMEDIATION.md](REMEDIATION.md) tracks each one. Fixed so far: long-timeline tick overflow, stereo export corruption, export at another audio rate, export mute/solo policy, delivery safety, the per-frame sequence copy, unscoped loader queries, and (milestone 1A) splitting reversed and animated clips, transition invariants through edits, and the track-lock policy, and (milestone 1B) shared-demuxer packet loss, audio seeking accuracy, stream-start normalisation, resampler delay and tail, and unsafe timestamp scanning, and (milestone 1C and the hardening that followed) nested-sequence and retimed audio, per-sample automation, head-trim animation drift, linked clips, the playback threading and seek races, device failure reporting, relink and ingest atomicity, and post-commit persistence failures. **Still open, and affecting rows above:**

- **FFmpeg decode:** positions within a stream whose container timestamps are coarser than a sample (Matroska's milliseconds) are only as exact as the container states them across a *timestamp discontinuity*; video seeking is verified on intra-only and short-GOP fixtures, not on a long-GOP production file; decode is software only and single-threaded per reader; the first audio seek into a coarse time-base file pays a one-off scan of its packets (about 100 ms for a one-hour, 350 MB file with a warm cache). The timestamp map reports a file with duplicate timestamps; its report for a file with no timestamps at all has no fixture.
- **Transitions:** sides are clamped to the clip edges in the picture (audio plays the media beyond the cut; picture holds the edge frame) and nothing checks that the media has handles; every picture transition is one linear mix.
- **Audio:** WSOLA pitch preservation has sine/chirp coverage but not production speech profiling; holds, reverse and rates outside 0.25â€“4x deliberately fall back to varispeed. There is no mixer UI, automation write mode, record arm or plug-in latency compensation.
- **Playback:** bounded decode/read-ahead is implemented and measured on a small warm H.264 fixture, but there is no render/presentation thread. Production-resolution scrub and playback-start latency have not been validated against the target.
- **Persistence:** journal v2 plus periodic snapshots recover durable project state and quarantine damage; the interactive undo history is intentionally not reconstructed after recovery.
- **Reporting:** `scripts/cross-check-parity.js --execute` runs the suites and requires every test a capability names to have passed; without the flag it checks only that the tests exist and says so.
- **Colour:** working/display transforms, ACES and four camera log families (no ACES output transform), 3D and 1D `.cube` LUTs (also on the card), a shipped pack of nine looks, PQ/HLG, tone mapping, gamut mapping and CPU scopes exist; OpenColorIO, an ACES output transform, 10-bit end-to-end output and HDR monitoring do not.

Until those are closed, treat the corresponding rows as "works for the tested cases".

## Performance

`scripts\bench.bat` measures the per-frame path at 1920Ã—1080 in Release. Current figures, and the effect of the optimisation pass:

| Case | Before | After |
|---|---:|---:|
| Composite, 1 track, 3 effects (8-bit source) | 67.7 ms | **37.3 ms** |
| Composite, 2 tracks, 3 effects (8-bit source) | 110.0 ms | **71.4 ms** |
| Composite, 4 tracks, 3 effects (8-bit source) | 190.4 ms | **140.8 ms** |
| Composite, 1 track, 1 effect (float source) | 46.9 ms | **18.4 ms** |
| Compile a plan, 16 tracks | 0.016 ms | 0.015 ms |
| Mix a 1024-frame block (4 tracks; see the log for the retimed and automated cases) | 0.005 ms | 0.017 ms |

What changed: layer buffers are reused rather than allocated per clip per frame (33 MB each at 1080p); every layer tracks the rectangle it actually wrote so effects and compositing skip untouched pixels; `DrawFrame` bounds its sweep by the projected corners of the transformed source; an untransformed clip whose source already matches the output is a straight copy instead of a bilinear resample; opaque pixels skip the un-premultiply divide; and effect ordering is no longer quadratic in stack depth. Every golden frame still matches, which is how the optimisation is known to be behaviour-preserving.

The software compositor is the reference implementation, and the Direct3D 11 compositor is the interactive path for the plans it can render: On this machine (AMD Radeon AI PRO R9700, Release build, `scripts\bench.bat --gpu`, perf/2026-10-07-gpu.txt) one 1080p layer with three effects composes in 36.9 ms in software and 2.7 ms on the GPU including the upload and the read-back (0.26 ms on the card); four layers 153.7 ms against 4.5 ms; reading and composing a 1080p H.264 picture takes 5.3 ms with software decode and upload and 2.0 ms with the hardware decoder and no copy. Debug-build figures in the test log are not comparable and are not quoted.

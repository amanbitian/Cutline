Interpretation
- Hardware-decoded media no longer schedules a duplicate software read-ahead decode. The GPU + read-ahead p95 fell from 19.9701 ms to 10.9055 ms and queued software decodes fell from 469 to zero.
- PrimeReadAhead now publishes work to its worker instead of compiling future frames on the caller. The synthetic contention probe fell from 109.13 ms to 0.0118 ms.
- The GPU compositor accepts up to 16 colour operations and eight LUTs per clip. GPU parity tests cover nine grades and two ordered LUTs.
- Neutral unsupported effects are ignored by the GPU eligibility check; an active unsupported effect still selects the software compositor.

Limits
- Results are from one machine and one source, and include frame read-back for the current monitor path.
- Active blur, sharpen, vignette, lens distortion, warps, keys, masks, graphics, optical-flow interpolation, and several other spatial effects still use the software compositor.
- The audit calls PrimeReadAhead for every CPU frame; latest-wins cancellation therefore prevents its background jobs from completing and does not represent ordinary forward playback cache-hit behavior.

Follow-up full-codebase audit

Correctness and scheduling
- If a hardware source opened but its first device-frame read failed, the cached device source used to remain non-null. Software read-ahead then stayed disabled even though rendering had fallen back to the CPU. DeviceFrameFor now drops that failed device source, and AHardwareDecoderFailureRestoresSoftwareReadAhead covers the case.

D3D11 target memory
- Before, EnsureTargets allocated two half-float canvases, two half-float transition layers, float and 8-bit output textures, and float and 8-bit staging textures for every compositor: 72 bytes/pixel, or 597,196,800 bytes (569.5 MiB) at 3840x2160.
- Targets are now allocated on demand. The normal 8-bit/no-transition path starts at 24 bytes/pixel, or 199,065,600 bytes (189.8 MiB), a calculated 379.7 MiB reduction. Transition layers are retained only after a transition needs them; float output/staging are created only for float output.

Remaining high-value work found by the audit
- Every GPU frame is still synchronously copied into a staging texture, mapped and copied to CPU memory, then copied into QImage. Existing 1080p measurements put read-back at roughly 2-3 ms, greater than the GPU compute pass. A shared D3D texture/Qt scene-graph monitor path is required to remove it.
- Any one unsupported active spatial effect rejects the complete playback plan and sends the whole frame through the software compositor. GPU kernels and eventually a per-layer hybrid execution plan are required.
- Every edit reloads the complete sequence graph and UpdateSequence clears decoded-frame, stretch, nested-frame and hardware-decoder state. Parameter dragging therefore discards source data even when no media changed. Change-classified invalidation is required.
- ExportClone explicitly disables the GPU, and ExportWorker serially renders, writes video, renders audio and writes audio. Export needs a bounded decode/compose/encode pipeline and a deliberate GPU-quality policy.
- Render-cache hits and stores clone full frames. Immutable shared backing or ownership transfer would remove about 3 ms in each direction at 4K in this probe.
- Render-key construction stats every referenced media/LUT asset per frame, transitions are scanned linearly per track, and active captions scan cues from the start of each track. These are secondary scaling issues for large projects.
